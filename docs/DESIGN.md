# cpfpの設計判断

- 対応コンパイラはAtCoderのGCC 15.2.0のみとし、`gnu++23`とBoost 1.88.0を使用します。
- LLVM/Clang系ツールはIDE、静的解析、コード整形に使用します。対応ビルド環境の代替には
  **しません**。
- 標準ライブラリやBoostの機能を別名で再公開しません。たとえば、
  `std::views::transform`、`std::views::filter`、`boost::hof::flow`は直接使用します。
- `cpfp::detail::partial_n<N>`を、固定引数個数のカリー化された関数オブジェクトに対する
  唯一の基盤とします。これは`boost::hof::partial`と
  `boost::hof::limit(integral_constant<N>{})`を合成したものです。
- 引数の**最大**個数を制限しても、呼び出し時の正確な引数個数が保証されるわけでは
  ありません。APIの契約はテストで検証します。
- 二項関数では通常のオペランド順を維持します。たとえば`sub(10)(3) == 7`です。
  設定値を受け取る述語では、設定を先、対象を最後に置きます。たとえば
  `between(10, 20)(x)`です。
- 束縛された引数はBoost.HOFの意味論に従って保持します（通常は値による保持です）。
  明示的な参照キャプチャ（`std::ref`）とその生存期間は呼び出し側の責任です。
- コアAPIでは、constexprに対応する標準関数オブジェクトまたは通常のラムダを使用します。
  Boost.Lambda2と`_1`、`_2`などのplaceholderはexperimentalの実装内部に限定し、公開
  名前空間へ再公開しません。実際に必要になるまでは、そのためだけのヘッダーも追加しません。
- 述語コンビネータ`all_pass`と`any_pass`には短絡評価が必要です。Lambda2の`&&`や`||`で
  短絡評価する述語を構築してはいけません。
- 標準ビューによる処理は遅延評価です。実体化と畳み込みは即時評価です。
- `on`は射影とメンバーポインタの呼び出しに`std::invoke`を使用します。
- `cpfp::experimental`は独立したヘッダーと名前空間に置きます。高度なモジュール
  （optional／expectedのapplicativeなど）は、型と失敗時の意味論を厳密に定義してから
  追加します。
- 公開APIには、型の役割と戻り値がclangdのホバーで分かるよう、1行の`///`疑似シグネチャを
  付けます。実装の説明や使用例は重複させず、必要な場合だけ別のコメントや文書へ記載します。
- 通常の数値APIおよび束縛APIにおける整数オーバーフロー、ゼロ除算、無効な`std::ref`は、
  呼び出し側の責任です。安全な代替APIには明示的な名前を付け、エラー情報を保持する
  戻り値を使用します。
- このスターターは動作する最小限の土台です。v0.1.0に必要な機能がすべて実装済みである
  ことを**保証するものではありません**。

## 今後の作業案

1. 引数個数と所有権の契約を厳密に定め、v0.1.0の最終的なAPI一覧を決定する。
2. プロパティテスト、参照カテゴリのテスト、コンパイル時テスト、ベンチマークを追加する。
3. メンバー関数の単なる別名ではなく、関数オブジェクトと合成を実質的に拡張する
   `experimental/optional.hpp`と`experimental/expected.hpp`を追加する。
